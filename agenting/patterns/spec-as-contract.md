# Спецификация как контракт между агентами

Работа передаётся агенту не описанием «сделай нормально», а документом, по которому приёмка выполняется механически: исполнитель делает, проверяющий сверяет с критериями, расхождение — повод для возврата, а не для спора.

**Когда использовать** — в цепочке больше одного агента (планировщик → исполнитель → проверяющий), работа идёт без человека в цикле, и «готово» должно означать одно и то же для всех троих. Особенно когда правки проверяются не глазами, а командами: сборка, тесты, `make validate`, наличие записи в каталоге.
Когда не брать: задача исследуемая, где критерии станут ясны только после работы (тогда первый прогон — выяснение критериев, и это отдельная задача); правка в одну строку; работа, где вкус важнее соответствия (выбор архитектуры, имена, UX-решения — там нужен человек, а не критерий).

## Форма документа

```markdown
# Спецификация: <что и зачем>

## Задача
Одним абзацем: что должно перестать быть правдой / стать правдой.

## Контекст
Где живёт: пути, команды запуска, чем мерить. Ссылки на правила раздела,
а не пересказ.

## Ограничения
Чего не трогать: файлы, публичные контракты, формат коммитов.
Разрешённые зависимости. Запрет на «попутные» правки.

## Критерии приёмки
- [ ] `make test` зелёный; добавлен тест на <конкретный случай>.
- [ ] `command X` печатает <ожидание> на входе <вход>.
- [ ] В <файл> добавлена запись с полями …; `make validate` зелёный.
- [ ] Поведение <крайний случай> описано и проверено тестом.

## Как проверять
Команды приёмки одна под другой, с ожидаемым выводом. Проверяющий запускает
их, а не читает дифф «на глаз».
```

Критерии должны быть исполняемыми или проверяемым взглядом за десять секунд. «Код читаемый», «логично устроено», «учтены крайние случаи» — не критерии: под них подпишется любой исполнитель и любой проверяющий, и ни один прогон ничего не доказывает.

## Правила приёмки

| Правило | Почему |
|---|---|
| Вердикт из трёх значений: `ок`, `не сделано`, `спецификация невыполнима` | свободный текст критики превращает возврат в переговоры |
| «Не сделано» — со ссылкой на конкретный неотвеченный критерий | исполнитель чинит пункт, а не угадывает, что имелось в виду |
| «Спецификация невыполнима» — первый класс успеха | честное «так нельзя» дешевле трёх раундов правок по неправильной задаче |
| Проверяющий не переписывает код | он теряет независимость: правящий проверяющий принимает свою работу |
| Раундов не больше N, потом — человек | третий раунд обычно повторяет первый: проблема в спецификации, а не в исполнении |
| Критерии не меняются задним числом | править критерии под готовый результат — способ принять плохую работу |

## Размер единицы работы

| Признак | Решение |
|---|---|
| Критериев больше десятка | дробить: приёмка не помещается в один прогон |
| Критерии про разные подсистемы | две задачи: проверяющий не должен разбираться в двух доменах сразу |
| «Сделать X и попутно навести порядок» | две задачи: вторая никогда не проверяется по критериям первой |
| Нужен результат предыдущей задачи | последовательно, с передачей результата, а не «пусть исполнитель сам догадается» |

## Связь с правилами проекта

Спецификация не пересказывает конвенции — она на них ссылается: формат записи, правила коммитов, требования к тестам живут в своих разделах ([../../docs/FORMAT.md](../../docs/FORMAT.md), [../../shared/commits.md](../../shared/commits.md), [../../shared/testing.md](../../shared/testing.md)). Пересказ = вторая правда, которая разъедется через месяц; это же правило работает и между людьми.
