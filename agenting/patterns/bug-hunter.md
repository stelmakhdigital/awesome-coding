# Охотник за дефектами по диффу

Автоматизация, которая периодически читает свежие изменения и заводит задачу на каждый обнаруженный дефект — с доказательством, дедупликацией и потолком результата.

**Когда использовать** — в проекте есть ветка, в которую сливается чаще, чем успевает разбираться человек, и часть дефектов типовая: незакрытая ошибка, гонка, обращение к nil-полю на пустом входе, запрос без таймаута, миграция без отката, сломанная инвариант-проверка. Частота — раз в сутки или на каждый пуш в защищённую ветку.
Когда не брать: проект до 10 тысяч строк с одним автором (правила окупаются, когда диффов больше, чем вы успеваете прочитать); команда, где нет обычая разбирать заведённые задачи (тогда вывод превращается в шум и убивает доверие к автоматизации); поиск «всего плохого сразу» — это аудит, его делают один раз и руками.

## Контур

```text
расписание / push
   └─ замок (flock)                      второй экземпляр не стартует
        └─ вход: git log <last_sha>..HEAD
             └─ пусто → выход 0, тихо
        └─ отбор файлов: без vendor/ и сгенерированного
        └─ агент: разбор диффа по правилам
             └─ фильтр: только падения/некорректная работа, не стиль
        └─ потолок: не больше N находок за прогон
        └─ на каждую: поиск существующей задачи по метке
             ├─ есть → комментарий с новым sha
             └─ нет → gh issue create (метка, доказательство, команда повтора)
        └─ чекпоинт last_sha = HEAD
```

## Правила, из которых состоит качество

| Правило | Формулировка для агента | Что даёт |
|---|---|---|
| Только поведение | «Сообщай о том, что можно уронить, испортить или неверно посчитать. Названия, формат, порядок импортов — не сообщать» | шум не тонит находки |
| Доказательство обязательно | «Укажи `файл:строка`, условие входа и что именно сломается. Не можешь сформулировать вход — не сообщай» | отсекает половину выдуманных дефектов |
| Проверка, а не догадка | «Если можно запустить тест или команду — запусти и приложи вывод» | задача становится проверяемой |
| Область поиска | «Смотри только изменённые файлы и их непосредственных вызывающих» | бюджет и точность |
| Потолок | «Не больше 3 находок за прогон; если их больше — выбери самые дорогие» | вывод читаем, трекер не завален |
| Дедупликация | «Перед созданием задачи найди открытую с той же меткой и тем же ключом» | нет десятков копий |
| Стоп-условие | «Если правил неясно или дифф непонятен — скажи прямо, не выдумывай» | честное «не знаю» вместо мусора |

## Тело задачи, которое переживёт спор

```text
Файл: internal/session/store.go:118
Вход: два параллельных PATCH /sessions/:id при stage=question
Эффект: второй запрос затирает ответ первого без ошибки; пользователь видит
        «сохранено» и потерянный ответ.
Почему: чтение и запись состояния не под одной транзакцией (BEGIN нет).
Повтор: go test ./internal/session -run TestConcurrentPatch
Найдено: прогон 2026-11-25, дифф 3f2a19c..81de0aa
<!-- ac-scan: internal/session/store.go:118 -->
```

Первые пять строк отвечают на «что, где, при каком входе, чем плохо, как повторить». Строка про прогон и sha отвечает на «откуда это взялось и почему раньше не видели». HTML-комментарий в конце — машиночитаемый ключ дедупликации ([../snippets/run-state.md](../snippets/run-state.md)).

## Метрики полезности

| Что | Зачем |
|---|---|
| Задач создано / закрыто «не дефект» | если доля отклонённых выше трети — правила надо сужать |
| Находок на прогон | ноль несколько прогонов подряд — автоматизация мертва, это видно только по числу |
| Время от прогона до первой реакции человека | полезность для команды, а не для отчёта |
| Ложные срабатывания по правилам | какие два правила дают больше всего шума — их и убирать |

Раз в квартал: выбрать десять закрытых задач прогона и посмотреть, сколько из них привели к правке кода. Ниже половины — автоматизация существует ради самого себя, и правильнее её выключить, чем «чуть подкрутить правила».
