# Единовременный прогон на flock

**Когда использовать** — любой прогон по расписанию или по событию, где второй параллельный запуск вреден: охотник за багами, синхронизация состояния, выгрузка отчёта. Часовой пояс сдвинулся, человек запустил вручную «потому что не видно, что работает», прошлый прогон завис и планировщик добавил новый — все три случая дают одновременную запись в одно место.
**Когда НЕ использовать** — взаимное исключение между разными машинами (`flock` на локальной файловой системе его не даёт: нужен замок в БД или в Redis — [../../database/snippets/redis.md](../../database/snippets/redis.md)); защита редкой операции, где достаточно `mkdir` (атомарен, но не чистится сам).

## Замок

```bash
#!/usr/bin/env bash
# shellcheck shell=bash
# run-once.sh — прогон, который не запускается вторым экземпляром.

# Механизм: flock на файловый дескриптор. Замок снимается ядром, когда процесс
# умирает — поэтому «протухший» замок здесь не чинят: pid-файлы так не умеют,
# и их чистка — отдельный источник багов.

set -euo pipefail

LOCK_DIR="${LOCK_DIR:-/var/tmp/ac-run}"
LOCK_TIMEOUT="${LOCK_TIMEOUT:-0}"   # 0 = не ждать, уходить сразу

# with_lock <имя> <команда...> — 0 если отработали, 3 если прогон уже идёт.
with_lock() {
  local name="$1"; shift
  local lockfile="$LOCK_DIR/$name.lock"

  mkdir -p "$LOCK_DIR"
  # 9: произвольный свободный дескриптор; важнее имени то, что он держится
  # всё время работы команды.
  exec 9>"$lockfile"

  if ! flock -n -w "$LOCK_TIMEOUT" 9; then
    printf '%s: прогон уже выполняется, выхожу\n' "$name" >&2
    return 3
  fi

  # Внутрь замка пишем идентификатор прогона: по нему видно, кто держит, когда
  # «зависший» прогон стоит в journalctl третьей минутой.
  printf '%s pid=%s\n' "$(date -Is)" "$$" >&9
  "$@"
}

work() {
  echo "работаю"
  sleep 0.3
  echo "готово"
}

if [[ "${1:-}" == "--self-test" ]]; then
  tmp="$(mktemp -d)"
  # shellcheck disable=SC2064  # tmp подставляется сейчас, а не в ловушке
  trap "rm -rf '$tmp'" EXIT

  # Два экземпляра стартуют одновременно: выиграть обязан ровно один.
  for _ in a b; do
    LOCK_DIR="$tmp" bash "$0" --run >"$tmp/$_.out" 2>"$tmp/$_.err" &
  done
  wait

  winners="$(grep -l работаю "$tmp"/*.out 2>/dev/null | wc -l)"
  skipped="$(grep -l "уже выполняется" "$tmp"/*.err 2>/dev/null | wc -l)"

  if [[ "$winners" != 1 || "$skipped" != 1 ]]; then
    printf 'FAIL: победителей=%s отклонённых=%s\n' "$winners" "$skipped" >&2
    exit 1
  fi
  echo "ok: один прогон прошёл, второй отклонён"
  exit 0
fi

case "${1:-run}" in
  --run) with_lock demo work ;;
  *) echo "использование: $0 [--self-test]" >&2; exit 64 ;;
esac
```

Прогон самопроверки:

```console
$ bash run-once.sh --self-test
ok: один прогон прошёл, второй отклонён
```

## Что с этим делают дальше

- `with_lock` оборачивает всё тело прогона, включая запись чекпоинта: иначе второй экземпляр допишет состояние, которого первый ещё не видел ([run-state.md](run-state.md)).
- Код 3 — штатный выход, а не ошибка: планировщик не должен считать его падением и поднимать алерт. Если планировщик считает — выходите с 0 и пишите строку в лог.
- `LOCK_TIMEOUT` больше нуля означает очередь: второй прогон дожидается первого. Для охотника за багами очередь обычно вредна — дешевле пропустить цикл, чем обработать устаревший вход.
- В контейнере с `readOnlyRootFilesystem` каталог замка должен быть tmpfs; `/var/tmp` на read-only корне даёт не «занято», а падение на `mkdir`.
- Замок не переживает перезагрузку и не работает по сети (NFS-семантика `flock` исторически дырявая): для «одна задача на кластере» нужен внешний замок.
