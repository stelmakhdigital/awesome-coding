# 0005. `reviewed` — потолок честности для разделов без тулчейна в CI

- **Статус:** accepted
- **Дата:** 2026-11-24

## Context

`verified` обязался быть фактом прогона, а не обещанием: `compiled` — код собрался
в CI закреплённым тулчейном, `executed` — ещё и отработал самопроверку.

Для `unity` (включая HLSL) и `kotlin` своего джоба в CI нет:

- Kotlin — компилятор плюс JVM, время сопоставимо с dotnet;
- Unity — редактор: гигантский образ, лицензионные ограничения,
  headless-сборка ради проверки синтаксиса сниппета несоразмерна задаче;
- HLSL — нужен компилятор шейдеров и графический контекст.

Соблазн — выставить этим разделам `compiled` «по аналогии с остальными». Это
прямая ложь в поле, которому доверяют больше, чем тексту.

## Decision

1. **Раздел без раннера в CI не поднимается выше `reviewed`**, и уровень не
   повышается вручную. Раздел `csharp` в этот CI входит с 2026-11-24: `dotnet
   build` .NET 10, проект на блок, NuGet по признаку блока. Первый же прогон
   поправил четыре записи — в них стояли API, которых не существует
   (`AddTransientHttpResilience`, `OptionsValidationResult`, `JsonDefaults`,
   `TimeProvider.LocalNow`): ровно тот класс ошибок, который `reviewed`
   поймать не может. В `tools/verify_snippets.py` язык без раннера попадает в список
   «без раннера (не проверялось)» и не получает вердикта.
2. **Отсутствие проверок — публично**: в шапке раздела написано, что примеры
   рецензированы и не прогонялись (см. `cicd/README.md`, `unity/README.md`).
3. **Раннер появится — уровень поднимется сам**: `make verify-fix` поднимает
   `verified` там, где прогон это доказал, и понижать его не будет.
4. **Исключение для kotlin**: два блока (`coroutines.md`, `http.md`) однажды
   прогонялись локальным `kotlinc` с версиями библиотек, названными в шапке
   раздела. Это weaker-форма доказательства: CI её не повторяет, и при смене
   закреплённой версии Kotlin уровень обязан быть перепроверен, а не унаследован.
5. **Минимальный суррогат, который не врёт**: там, где часть записи всё же
   выполнима (bash-обвязка, конфиг, SQL-фрагменты вокруг Kotlin-кода), проверяется
   выполнимая часть, а уровень ставится по факту прогона блоков, а не по языку
   раздела целиком.

## Consequences

- ✅ Поле `verified` остаётся полезным: отсутствие проверки отличимо от
  присутствия, и читатель знает, где тоньше лёд.
- ✅ Нет соблазна «приукрасить» раздел ради ровной картинки в таблице статусов.
- ❌ В `kotlin` и `unity` возможны ошибки, которые компилятор ловит за секунду:
   опечатки в сигнатурах, устаревший API версии. Осознанный размен.
- ❌ Dotnet-джоб — самый тяжёлый в матрице (образ ~1 ГБ, NuGet нужен доступ в
   сеть), потому ему ограничена параллельность (`--jobs 2`) и контейнер
   запускается под uid хоста: иначе артефакты сборки остаются root-owned в
   примонтированном каталоге и временный каталог с хоста не удалить.
- ❌ Раздел не protected от дрейфа версии: `make check-versions` и
  `make check-stale` — единственная страховка, плюс ручная перепроверка при
  смене закреплённой версии.
- **Когда пересматривать:** для kotlin — когда kotlinc-раннер перестанет быть
  лотереей по времени (или когда смена закреплённой версии заставит перепроверять
  локальный прогон вручную). Unity и HLSL — практически никогда: для них
  `reviewed` и есть проектная норма.
