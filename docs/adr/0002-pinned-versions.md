# 0002. Закреплённые версии технологий с fallback

- **Статус:** accepted
- **Дата:** 2026-09-06

## Context

Сниппеты и правила пишутся под конкретные версии (API, идиомы, дефолты
меняются между мажорами). Без закрепления версий:
- агент не знает, какую идиому писать — «актуальную» по данным обучения
  (которые могут быть устаревшими или, наоборот, описывать ещё не вышедшие фичи);
- разные записи репозитория противоречат друг другу по версиям;
- невозможно проверить код сниппета (на чём компилировать?).

## Decision

1. **Одна закреплённая версия на технологию** — таблица «Версии» в `AGENTS.md`
   (единственный источник), зеркало в `index/manifest.yaml` (`languages.*.version`).
2. **Fallback** — предыдущая стабильная мажорная версия: если проект агента
   на более старой, применяется fallback, а не закреплённая.
3. **Дата проверки** в заголовке таблицы: версии закреплены «на дату»,
   а не «навсегда».
4. **Периодическая сверка**: `make check-versions` (раз в квартал) сравнивает
   закреплённые версии с актуальными; при обновлении — перепроверка затронутых
   сниппетов и обновление `verified` в manifest.

## Consequences

- ✅ Детерминированность: «идиоматичный код» имеет точное определение.
- ✅ Сниппеты проверяемы: компиляция/запуск — на закреплённой версии.
- ✅ Fallback покрывает большинство реальных проектов без раздвоения репозитория.
- ❌ Репозиторий отстаёт от «самых свежих» фич до квартального аудита —
  осознанная цена предсказуемости.
- ❌ Обновление версии — работа (перепроверка сниппетов), а не правка числа;
  риск «забытого аудита» компенсируется `make check-versions` и CI.
