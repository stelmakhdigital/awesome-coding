# 0003. Без ORM в Go: database/sql + pgx / sqlc

- **Статус:** accepted
- **Дата:** 2026-09-06

## Context

Go-экосистема предлагает ORM (GORM, ent, sqlboiler), но они тянут за собой
рефлексию, магию генерации и скрытые запросы. Для кодинг-агента это особенно
плохо: ORM-код невозможно проверить «на глаз» — агент не видит, какой SQL
реально уйдёт в БД, и не может предсказать N+1 и ленивые загрузки.

## Decision

1. **Базовый уровень — `database/sql` + драйвер** (`pgx/v5/stdlib`):
   явные SQL-запросы, пул соединений, транзакции, `*Context`-методы
   (см. `go/snippets/sql.md`).
2. **Типобезопасность — `sqlc`** при сложных запросах/миграциях: SQL пишется
   явно, Go-код генерируется — агент видит и то, и другое.
3. **ORM (`ent` и аналоги) — только** при сложной доменной модели с
   graph-запросами (указано в `go/decisions.md` как исключение).

## Consequences

- ✅ SQL всегда явный: N+1, индексы, планы — видны и проверяемы.
- ✅ Минимальные зависимости: `database/sql` — stdlib, драйвер — один пакет.
- ✅ Агент может написать корректный код, опираясь только на сниппет и правила.
- ❌ Больше ручного кода на CRUD, чем с ORM; компенсируется sqlc-генерацией.
- ❌ Сложные доменные графы (много сущностей, связи) — больнее, чем в `ent`;
  осознанное исключение, а не запрет.
