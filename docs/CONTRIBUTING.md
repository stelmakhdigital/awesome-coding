# CONTRIBUTING

## Добавление записи

1. Прочитайте [FORMAT.md](FORMAT.md).
2. Создайте файл в нужном каталоге: `<lang>/snippets/` или `<lang>/patterns/`.
3. Заполните frontmatter; убедитесь, что `id` уникален (проверьте `index/<section>.yaml`).
4. Добавьте запись в `index/<section>.yaml` (раздел по имени файла), `verified: none`.
5. Прогоните код через тулчейн: `python3 tools/verify_snippets.py --record <id>`
   (или `make verify` по всему репозиторию). Прошёл — `make verify-fix` поднимет
   `verified` до `compiled` и обновит даты в каталоге и frontmatter.
6. Go-запись — `make gofmt RECORD=<путь>`: вердикт `fmt` ломает CI так же, как `fail`.
7. Проверьте: ссылки работают, теги осмысленны, `make validate` зелёный.

## Чек-лист

- [ ] Frontmatter полный, `id` уникален
- [ ] Есть «Когда использовать / Когда НЕ использовать»
- [ ] Код проходит `verified`-прогон своего языка (таблица в [FORMAT.md](FORMAT.md))
- [ ] Код отформатирован тулчейном языка (`make gofmt` для Go)
- [ ] Есть секция Pitfalls
- [ ] `index/<section>.yaml` обновлён (в том числе `verified` — как факт прогона)
- [ ] Все ссылки валидны (относительные, без битых)
- [ ] `updated` актуален

## Коммиты (для агентов и людей)

### Сообщение

- Язык — русский, без conventional-префиксов (`feat:`, `fix:`).
- Первая строка — что и зачем, ≤ 72 символа: `Туллинг: CI, make search, mermaid-валидатор`.
- Тело (опционально) — детали: что изменено, почему, как проверено.
- **Один коммит — одна забота**: туллинг, контент и процессы — разные коммиты.

### Перед коммитом

- `make validate` (и `make validate-mermaid`, если менялись mermaid-блоки) — зелёные.
- Правка в `tools/` — зелёный `make test` и тест на новое поведение (что покрывается — блок «Тесты туллинга» в `docs/FORMAT.md`).
- Индексы обновлены в том же коммите, что и контент: `index/<section>.yaml`,
  README раздела. Блок «Статус разделов» основного README не правится руками —
  `make readme` (он генерируется из каталога, и `make validate` это проверяет).
- `verified` в каталоге `index/` отражает фактическую проверку: `executed` / `compiled` /
  `reviewed` / `none` — не обещание, а факт.
- `git status` — нет чужих файлов (`node_modules/`, временные артефакты).

### Разделение

- Файл с изменениями разных забот (например, manifest: новое поле + новые записи)
  разделяется на коммиты: сохранить финальную версию → вернуть HEAD → применить
  часть → коммит → применить остаток → коммит.
- Ошибка, найденная до коммита, — исправляется молча; найденная после — отдельный
  коммит (или `amend`, если коммит ещё не запушен).

### Push

- После коммита — push в `master` (PR-флоу в репозитории нет).
- Force-push в `master` — запрещён.

## Релиз

Версия — git-тег `vN.N` (semver). Агенты пинят её в `skills/awesome-coding/SKILL.md`,
поэтому тег — единственная точка, по которой кэш агента понимает, что он читает.

1. `make validate` и `make check-versions` — зелёные.
2. Блок CHANGELOG и пин — инструментом, а не `str.replace`:
   `python3 tools/release.py prepare --version vN.N --body entry.md` (дата — день
   коммита, `--date` другого дня отвергается).
   Тело блока — что добавлено/изменено с прошлого тега (источник —
   `git log <prev-tag>..HEAD --oneline`). Правка руками опасна: несовпавший якорь
   заголовка не вставляет блок молча, и три релиза так вышли с пином без записи.
3. Пин и CHANGELOG — одним коммитом; перед тегом `make release-check VERSION=vN.N`.
   Согласованность пина и верхнего блока CHANGELOG сверяется и в CI на каждый
   push (`python3 tools/release.py check` без версии) — обряд, который требует
   запустить проверку руками, проверкой не считается.
4. `git tag -a vN.N -m "…" && git push origin master vN.N`.
5. MAJOR — только если сломан роутинг агента (структура разделов, формат frontmatter,
   смысл `verified`); тогда же — ADR в `docs/adr/`.

## Стиль

- Плотность сигнала: без вводных и повторов.
- Примеры кода важнее прозы.
- Правила в `rules.md` — краткие, с причиной.
- Версии: используйте закреплённые в `AGENTS.md`; если запись требует более новую — поднимите `min_version` и укажите в тексте.

## Языковые инструменты проверки

CI (`make verify`) гоняет обязательный минимум в контейнерах — какой именно, описано
в таблице прогона [FORMAT.md](FORMAT.md). Ниже — инструменты локальной/IDE-проверки,
которые шире CI (линт, санитайзеры) и никто не отменял.

| Язык | Инструменты |
|---|---|
| Go | `gofmt`, `go vet`, `golangci-lint` |
| TypeScript | `tsc --strict`, `eslint` |
| JavaScript | `eslint` |
| Python | `ruff`, `mypy` |
| C | `clang -Wall -Wextra -Werror`, sanitizers |
| Bash | `shellcheck` |
