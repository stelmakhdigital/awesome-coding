# FORMAT.md — спецификация формата записей

Единый источник правды о формате всех записей репозитория.
Перед созданием записи прочитайте этот документ полностью.

## Общие правила

- **Один файл = одна запись.** Имя файла: `kebab-case`, существительное, без префикса языка (язык определяется каталогом): `http-server.md`, а не `go-http-server.md`.
- Файлы: UTF-8, Markdown, завершаются символом новой строки.
- У каждой записи — YAML frontmatter (обязателен).
- Код в блоках всегда с указанием языка: ` ```go `, ` ```ts `, ` ```python `, ` ```c `, ` ```bash `.
- Код должен быть **компилируемым/запускаемым** и идиоматичным для закреплённой версии языка (см. `AGENTS.md`).
- Плотность сигнала: без воды. Примеры важнее описаний.

## Frontmatter (обязательные поля)

| Поле | Тип | Описание |
|---|---|---|
| `id` | string | Уникальный в репозитории: `<lang>-<name>`, напр. `go-http-server` |
| `title` | string | Человекочитаемое название |
| `lang` | string | Имя раздела: `go` \| `typescript` \| `javascript` \| `react` \| `python` \| `c` \| `bash` \| `csharp` \| `kotlin` \| `unity` \| `shared` \| `architecture` \| `database` \| `messaging` \| `cicd` \| `pm` \| `agenting` |
| `min_version` | string | Минимальная версия языка, напр. `"1.22"`, `"3.11"`, `"C23"`, `"5.2"` |
| `category` | string | `snippet` \| `pattern` \| `rule-set` \| `idioms` \| `decisions` \| `concept` |
| `tags` | [string] | 3–8 тегов, lowercase, для поиска. Только строки: числовое значение (`429`) кавычится, иначе YAML прочитает его числом и валидатор завернёт |
| `status` | string | `stable` \| `experimental` \| `deprecated` |
| `updated` | date | Дата последнего содержательного обновления, `YYYY-MM-DD` |

## Каталог записей (`index/`)

- `index/manifest.yaml` — **шапка**: `version`, `updated`, `sections`
  (список разделов — для агентов и туллинга), версии языков
  (`languages.*.version`).
- `index/<section>.yaml` — **записи одного раздела** (go, typescript, …, shared,
  architecture, database, messaging, cicd, pm). Агент читает только нужный файл.

Каждая запись:

| Поле | Тип | Описание |
|---|---|---|
| `id` | string | Совпадает с `id` в frontmatter файла |
| `title` | string | Совпадает с `title` в frontmatter файла |
| `path` | string | Путь к файлу относительно корня репозитория |
| `tags` | [string] | Теги для поиска (совпадают с frontmatter; проверяется валидатором) |
| `status` | string | Совпадает со `status` в frontmatter |
| `verified` | string | Уровень проверки кода: `compiled`, `executed`, `reviewed`, `none`. Что именно прогоняется под каждым уровнем — таблица ниже. Для `category: snippet/pattern` с кодом на go/c/csharp/kotlin/python/bash/ts/js/sql `none` запрещён — проверяется валидатором. Декларативные блоки (dockerfile, yaml, protobuf) и hlsl (компилируется только в Editor) в расчёт не идут |
| `updated` | date | Дата последнего содержательного обновления; обязан совпадать с `updated` в frontmatter файла. Позволяет агенту/кешу проверять свежесть записи, не читая файл |

Правила:

- `id`, `title`, `status`, `tags` обязаны совпадать с frontmatter — проверяется валидатором.
- `verified` отражает **факт проверки**, а не обещание: «код должен компилироваться» ≠ `compiled`.
- При повышении уровня проверки (например, `reviewed` → `compiled`) обновляйте
  `index/<section>.yaml` и дату `updated`.
- `updated` в записи каталога обязан совпадать с `updated` в frontmatter —
  проверяется валидатором. При содержательном изменении записи обновите обе.
- Имя секционного файла = название раздела; новые разделы — только после
  расширения `ALLOWED_SECTIONS` в `tools/validate.py`.

## Что стоит за `verified`

`make verify` (`tools/verify_snippets.py`) вытаскивает код-блоки записей и гоняет
их в Docker. `compiled` означает ровно прогон из своей строки таблицы — ни «должно
собираться», ни «на моей машине собралось».

| Язык | Прогон |
|---|---|
| go | `gofmt -l` + `go build ./...`; запись = один модуль, блоки — его пакеты |
| ts | `tsc --noEmit --strict --lib es2024` (typescript, @types/node, zod, vitest) |
| tsx | `tsc --noEmit --strict --lib es2024,dom --jsx react-jsx` (react 19, @types/react, Testing Library) |
| js | `node --check` |
| python | `compile()` на 3.14: синтаксис и байт-код (импорты третьих сторон не разрешаются) |
| c | `gcc -std=c23 -fsyntax-only -Wall -Wextra` |
| bash, sh | `shellcheck -f gcc` (код 0 — замечаний нет) |
| sql | psql на PostgreSQL 18 (Docker): блоки записи выполняются по порядку в одной схеме; ссылка на таблицу из чужого блока — `deps` |
| llm | по языку кодового блока (go, python) — отдельного тулчейна у раздела нет |
| csharp | `dotnet build` .NET 10: проект на блок (Exe, с падением на Library для блоков без точки входа), `FrameworkReference Microsoft.AspNetCore.App`, NuGet-пакеты по признаку блока (OpenApi, resilience, xunit). Блоки с Unity-API в прогон не идут: их собирает только Editor |
| kotlin, hlsl | раннера нет: `verified` ставится вручную (kotlinc локально с зафиксированными версиями в шапке раздела, Unity Editor) |

Вердикты прогона: `ok`, `fail` (код битый — править запись), `fmt` (gofmt
переформатирует блок), `deps` (не хватает сгенерированных или чужих пакетов —
например grpc-стабов или пакета из соседней записи), `fragment` (блок без
`package` — проверить нельзя, и выдумывать за автора обёртки не нужно).

`fail` и `fmt` дают ненулевой exit code (в CI ломают сборку): код отсюда копируют
как есть. `deps` и `fragment` — не ломают: их проверить нельзя, а не сломано.
У SQL в `deps` попадают запросы с плейсхолдерами (`$1`): значения подставляет
драйвер, `psql` их не знает — предложение при этом разобрано и проверено по схеме.

`make verify-fix` поднимает `verified` до `compiled` и обновляет `updated` в
каталоге и frontmatter там, где прогон это доказал. Уровень только растёт:
`executed` не понижается. `--record <id>` / `--section <раздел>` — проверить
одну запись или раздел после правки.

`make gofmt RECORD=<путь>` форматирует go-блоки записи на месте: прогоняет их
через gofmt в том же контейнере и вставляет обратно. Вердикт `fmt` — это
форматирование, а не содержимое, и править табы глазами незачем.

## Что проверяет `make validate`

| Проверка | Что смотрит |
|---|---|
| frontmatter | обязательные поля, значения `status`/`verified`/`lang`, уникальность `id`, даты |
| manifest | `index/*.yaml` ↔ файлы: пути, `id`/`title`/`tags`/`updated` как во frontmatter, `verified` честен для записей с кодом |
| indexes | `README.md` каталога упоминает все .md этого каталога |
| structure | у `category: snippet` есть «Когда использовать», «Когда НЕ использовать», `Related`; у `pattern` — «Когда использовать» и `Related` |
| text | в прозе нет CJK-символов и слов, набранных в чужой раскладке (код и inline-код не проверяется) |
| aliases | `index/aliases.yaml`: ключ в форме тега, не совпадает с тегом/id, все target-ы — существующие id |
| readme | блок «Статус разделов» в README совпадает с генерацией из каталога |
| links | относительные ссылки ведут на существующие файлы |

Отдельно: `make validate-structure`, `python3 tools/validate.py --check structure`.

## Тесты туллинга (`make test`)

`tools/test_tools.py` (stdlib unittest, зависимостей сверх PyYAML нет) проверяет
сам тулинг: вердикты раннеров (`classify`), разбор формата, текстовые и
структурные проверки, каталог, алиасы и порядок поиска. Живой тулчейн и сеть
(verify, check-versions, mermaid) здесь не проверяются — это задача CI.

Правка `tools/*.py` — добавьте тест на новое поведение. Зелёный `make validate`
означает «записи в порядке» только пока сам валидатор не сломался.

## Поиск (`tools/find.py`)

Каталог — источник истины поиска, текст записей не читается (для этого есть `rg`).
Результат упорядочен по близости к запросу, при равных — по id.

Оценка одного слова против записи:

| Балл | Совпало |
|---|---|
| 100 | тег целиком |
| 70 | `id` целиком |
| 60 | тег содержит слово — дословно или в другой форме |
| 40 | слово в `title` — дословно или в другой форме |
| 20 | слово в `id` |

Плюс **80** поверх, если слово записано в `index/aliases.yaml` как имя этой
записи. Алиас — явный указатель, он складывается со словами запроса, а не
заменяет их: «инструменты модели» сильнее, чем просто «инструмент».

Словоформа — общее начало слов: «клиент»/«клиенты», «миграция»/«миграции»,
«параллельность»/«параллельности» (расхождение не больше чем в последнем символе,
слова короче пяти символов не сравниваются: у «час» и «часто» общее начало есть,
понятия разные). Словаря окончаний нет намеренно: список окончаний
разъезжается со словами репозитория, а общее начало ошибается редко. Совпадение
дословное и совпадение словоформы весят одинаково — ступень ниже делила балл там,
где разницы нет, и «миграция» уходила за упоминание в чужом заголовке
сильнее, чем за имя записи.

**Запрос разбирается по словам.** Однословный запрос идёт по шкале выше;
многословный суммирует оценки слов, дословное совпадение всей фразы добавляет
+50, при равных суммах вперёд идёт запись, у которой совпало больше слов. При равных баллах и равном числе
совпавших слов практическая запись идёт вперёд справки: сниппет и паттерн раньше
правил и таблиц решений. Союзы и местоимения («и», «в», «для») выбрасываются: «и» — подстрока большинства
названий. Короткая кириллица тоже выпадает (там почти всегда предлоги), короткая
латиница остаётся («go», «ci», «js» — это названия). Слово пробуют в трёх
формах: раздельно, через дефис и слитно — в заголовках разделитель пробел, в
тегах дефис, а React-хуки называются слитно (`useeffect`).

Иначе говоря: запрос «медленные клиенты отвал» ищет запись, где эти три понятия
перечислены в названии и тегах, хотя такой строки нет ни в одном поле.

`index/aliases.yaml` — лексика, которой нет в тегах записей:

```yaml
aliases:
  upsert: [database-transactions, kotlin-room, messaging-outbox]
  доступ: [shared-security, shared-authentication]
```

Алиас отвечает на запрос, а не утверждает связь между записями. Если слово — то,
как запись называет себя сама, заводите тег, а не алиас: иначе одна и та же
информация начнёт жить в двух местах. Алиас нужен для чужой лексики: «upsert» при
теге `on-conflict`, «openid» при теге `oidc`.

**Русские ключи в алиасах — часть дизайна.** Теги каталога — латиница, а ищут по
русски: «остановка» против `shutdown` не совпадёт ни при какой морфологии, дело в
другом алфавите. Ключ даётся в именительном падеже единственного числа, формы
подбирает сравнение по словуформе («отмена» покрывает «отменить»). Валидатор
разрешает в ключах кириллицу, требуя прежнюю форму: строчные, дефисы, без пробелов
и подчёркиваний.

Порядок проверяется формулировками задачи, а не однословными тегами:
`RealIndexSearchTest` в `tools/test_tools.py` держит около пятидесяти реальных
запросов и ждёт нужную запись в топ-3. Однословные проверки (`make search
Q=async`) главный отказ не ловили: запрос из двух слов не давал ничего.

## Структура сниппета (category: snippet)

```markdown
# <Title>

**Когда использовать** — одна-две фразы.
**Когда НЕ использовать** — одна-две фразы + ссылка на альтернативу.

## Код
```<lang>
...
```

## Pitfalls
- Список типичных ошибок при использовании.

## Alternatives (опционально)
- Альтернативные подходы и когда они лучше.

## Related (опционально)
- Ссылки на связанные записи (относительные markdown-ссылки).
```

## Формат правил (rules.md, category: rule-set)

- Группировка по темам: `## Ошибки`, `## Именование`, `## Конкурентность` и т.д.
- Каждое правило — одна строка: `✅` (обязательно) или `❌` (запрещено) + суть + код-пример, если нужно.
- Правило без причины — плохое правило: указывайте следствие нарушения.
- `rules.md` — это **жёсткий** слой: агент обязан его соблюдать.

## Формат паттерна (category: pattern)

```markdown
# <Title>

**Проблема** — что решает паттерн.
**Решение** — суть в 2–4 предложениях.
**Когда использовать / Когда НЕ использовать**

## Код
Референсная реализация.

## Trade-offs
- Плюсы / минусы / альтернативы.

## Related
```

## Формат таблиц решений (decisions.md, category: decisions)

```markdown
## <Область, напр. HTTP>

| Задача | Рекомендация | Альтернатива | Когда |
|---|---|---|---|
| Роутинг | stdlib (1.22+) | chi | сложные мидлвари |
```

- Рекомендация — конкретная библиотека/подход + минимальная версия.
- «Когда» — условие, при котором выбирают альтернативу.

## Кросс-ссылки

- Только относительные markdown-ссылки.
- Из сниппета в паттерн: `../patterns/<name>.md`; между сниппетами: `<name>.md`.
- Битые ссылки запрещены.

## Статусы

- `stable` — рекомендуемая, проверенная на production.
- `experimental` — новая/нестабильная функциональность; помечать явно в тексте.
- `deprecated` — не использовать в новом коде; указать замену в frontmatter-комментарии и в тексте.
