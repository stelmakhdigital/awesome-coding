# Documentation — принципы

**Когда использовать** — создание/изменение документации проекта: README, AGENTS.md, docs/, ADR, inline-комментарии.
**Когда НЕ использовать** — автогенерируемые API-доки (OpenAPI/protobuf — контракт и есть документация).

## Иерархия документации

| Слой | Файл | Зачем | Для кого |
|---|---|---|---|
| 1. Назначение | `README.md` | что это, зачем, quickstart | люди + агенты |
| 2. Роутер | `AGENTS.md` | куда идти за какой задачей | кодинг-агенты |
| 3. Детали | `docs/` | спецификации, how-to, форматы | люди |
| 4. Решения | `docs/adr/` | почему сделано так | люди + агенты |
| 5. Inline | комментарии в коде | неочевидное «почему» рядом с кодом | все |

1. **README отвечает «что и как начать»**, а не «как устроено» — устройство: в `docs/` или в коде.
2. **`AGENTS.md` — роутер, а не дамп контента**: таблица «задача → куда», 50–100 строк.
3. **Один документ = одна тема**; длинный документ — разбить на `docs/` со ссылками из README.

## Шаблон README

1. **Назначение** — 1–3 предложения: что это, для кого.
2. **Quickstart** — минимальные шаги до работающего результата (установка, запуск, тест).
3. **Структура** — дерево каталогов с однострочными комментариями (только значимые).
4. **Статус** — что проверено/закончено, закреплённые версии.
5. **License**.

## ADR (Architecture Decision Records)

- **Одно решение — один файл**: `docs/adr/NNNN-short-title.md`, номер монотонно растёт.
- Структура: **Context** (какая проблема) → **Decision** (что выбрали) → **Consequences** (плюсы/минусы, что стало легче/сложнее).
- Статусы: `proposed → accepted → superseded by NNNN / deprecated`.
- Писать **до** реализации неочевидных решений; очевидные решения ADR не требуют.
- ADR **не удаляют**: ошибочное решение помечают `superseded`, решение — в новом ADR.

## Agent-first

1. **Машиночитаемая структура**: таблицы, списки, стабильные имена — агент читает только нужное.
2. **Относительные ссылки без битых** — битая ссылка это баг.
3. **Дата `updated`** в важных документах — по ней судят о свежести.
4. **Доки и код — один коммит**: изменение поведения без изменения доков — незавершённое изменение.
5. **Плотность сигнала**: примеры и таблицы вместо прозы; без воды.

## Правила (жёсткий слой)

- ✅ Код-примеры в доках — минимальные, запускаемые, совпадают с кодом.
- ✅ Неочевидное «почему» — комментарием рядом с кодом, а не только в доках.
- ✅ Диаграммы для потоков/взаимодействий — см. [mermaid.md](mermaid.md).
- ❌ Скриншоты кода/UI — их нельзя скопировать, они устаревают.
- ❌ Дублирование кода в доках — док устареет; ссылка на файл вместо копии.
- ❌ «TODO: доки» — либо написать, либо убрать задачу из списка.
- ❌ Док, противоречащий коду — код побеждает, док чинят в том же коммите.

## Антипаттерны

- ❌ «Год-README» на 300 строк — разбить: README (роутер) + `docs/`.
- ❌ Док о «идеальной» системе, а не о фактической.
- ❌ Changelog вместо доков — changelog это «что изменилось», а не «как работает».
