# Code Review — правила для агентов

**Когда использовать** — ревью diff/PR на любом языке; самопроверка своего кода перед коммитом.
**Когда НЕ использовать** — дублирование автоматических проверок (стиль ловит линтер); ревью сгенерированного кода (sqlc/protobuf — ревьюите исходники: SQL/.proto).

## Порядок проверок

1. **Корректность** — делает ли код то, что просит задача; граничные случаи, пути ошибок.
2. **Безопасность** — инъекции, секреты, авторизация, path traversal, TLS (см. [security.md](security.md)).
3. **Производительность** — N+1, неограниченные буферы, аллокации в hot path, блокировки в async.
4. **Поддерживаемость** — именование, дублирование, мёртвый код, сложность.
5. **Тесты** — новые пути покрыты; тесты детерминированы.
6. **Стиль** — последним; если есть линтер — не нитпикить.

## Серьёзность замечаний

| Уровень | Что это | Действие |
|---|---|---|
| `blocker` | баг, потеря данных, дыра в безопасности | обязательное исправление до мёрджа |
| `major` | дефект дизайна, нет теста на критичном пути | желательно исправить |
| `minor` | читаемость, именование | можно исправить позже |
| `nit` | стиль | не блокирует |

## Правила

✅

- Ревьюите diff, не весь файл — но читайте контекст изменённых функций.
- Проверяйте утверждения: «работает» — прогоните тесты/сборку; «нет регрессии» — прогоните существующий тест-сьют.
- Языковые правила — из `<lang>/rules.md`; версии — закреплённые (таблица «Версии»).
- Комментарий = `file:line` + что + почему + как исправить. Один комментарий — одна проблема.
- Нашли проблему — предложите фикс (diff), а не только «тут неверно».
- Задача/спека не читалась — сначала прочитайте: без неё невозможно отличить баг от намерения.

❌

- Не выдумывайте требования: нет в задаче/спеке — не требуйте (задайте вопрос).
- Не переписывайте чужой код под свой стиль, если это не blocker.
- Не дублируйте линтеры: то, что ловят golangci-lint/eslint/ruff/shellcheck, не комментируйте.
- Не блокируйте на nits: «было бы хорошо» ≠ «обязательно исправить».
- Не ревьюите по памяти: проверяйте реальный API и версию, а не «как я помню».

## Чек-лист безопасности (всегда)

- [ ] Нет секретов в коде, логах, истории коммитов (ключи, токены, пароли)
- [ ] Внешний ввод валидируется: SQL, shell, пути, URL, десериализация
- [ ] AuthN/AuthZ: доступ проверяется, а не «доверяется»
- [ ] TLS: нет отключённой верификации (`-k`, `InsecureSkipVerify`, `verify=False`)
- [ ] Ошибки не раскрывают внутренности (stack trace, SQL, пути)

## Чек-лист производительности

- [ ] Нет N+1-запросов в циклах
- [ ] Нет неограниченных буферов/очередей (лимиты, таймауты)
- [ ] Нет блокирующих вызовов в async/event loop
- [ ] Кэши — с политикой истечения, не «вечно»
- [ ] Дорогие операции (логирование, сериализация) — вне hot path

## Самопроверка перед коммитом (свой код)

1. Линтеры/валидаторы — чистые.
2. Перечитайте diff: у каждого куска есть причина существовать?
3. Не сломан ли контракт (API, схема, документация, метаданные)?
4. Тесты зелёные и покрывают новый путь.

## Pitfalls

- **Резиновое клеймо**: «LGTM» без чтения. Ревью, не нашедшее ничего, — либо отличный diff, либо плохое ревью.
- **Один проход по большому diff**: большие изменения ревьюите по подсистемам.
- **Перенос планки**: после фикса не добавляйте новых требований — скоуп согласуйте заранее.
- **Ревью без контекста**: diff без задачи/спеки/решений (ADR) — половина багов не видна.
- **Генерированный код**: правки в сгенерированном коде — blocker; фикс должен идти в источник генерации.
