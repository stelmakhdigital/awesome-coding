# Архитектура

Языконезависимые архитектурные паттерны и DDD. Применяется в первую очередь к
Go/TS/Python-приложениям; для C/Bash — только на уровне «границы модулей».

## Уровни DDD (выбирайте по сложности проекта)

| Уровень | Что | Когда |
|---|---|---|
| 0 | Без DDD: transaction script + слоистая архитектура | скрипты, CRUD, прототипы, простые сервисы |
| 1 | Тактические паттерны (entity, value object, aggregate) | бизнес-логика в ядре, сложные инварианты |
| 2 | + стратегический дизайн (bounded contexts) | несколько доменов, несколько команд |
| 3 | + event-driven / CQRS / Event Sourcing | асимметрия чтения/записи, аудит истории, распределённые события |

**По умолчанию — уровень 0.** Поднимайтесь на уровень выше только при конкретной
проблеме: инварианты нарушаются в сервисах, границы модулей неясны, данные
двух команд конфликтуют. Архитектура — средство, а не цель: каждый дополнительный
слой должен окупаться.

## Базовые принципы (для всех уровней)

1. **Зависимости направлены внутрь**: домен не знает об инфраструктуре (БД, HTTP, мессенджеры).
2. **Границы важнее внутренней структуры**: чёткие модульные границы ценнее «красивой» внутренней архитектуры.
3. **Поведение в модели, а не в сервисах** (при уровне ≥ 1): иначе — anemic domain model.
4. **Одна сущность — один владелец данных**: модуль/сервис владеет своими данными, другие обращаются через его API.
