# Требования — сбор и форматы

**Когда использовать** — фаза 1 SDLC (Definition) и любое добавление в scope.
**Когда НЕ использовать** — сбор требований «на весь продукт на 5 лет» (горизонт —
текущая фаза + 1, дальше — гипотезы).

## Источники (и их вес)

| Источник | Что даёт | Ограничение |
|---|---|---|
| Интервью с пользователем | Проблема, контекст, поведение | Мнение ≠ требование; малая выборка → много шума |
| Опрос ([survey.md](survey.md)) | Частота, приоритеты, сегменты | Глубина меньше, чем в интервью |
| Аналитика/логи | Фактическое поведение | Нет «почему» |
| Обратная связь (баги, письма) | Боли, edge-cases | Выборочная (злится — пишет) |
| Запрос стейкхолдера | Scope, обязательства | Требует проверки против ICP |

Правило: каждое требование в roadmap трассируется к источнику
(«из интервью #3», «опрос, 12/40», «аналитика: 30% уходят на шаге 2»).
Требование без источника — гипотеза, помечается как таковая.

## Форматы

**User story** (для функциональных требований):
```
Как <роль>, я хочу <действие>, чтобы <ценность>.
Acceptance criteria:
- Given <контекст>, when <действие>, then <результат>.
```

**NFR** (нефункциональные — явно, с числами):
```
- Производительность: p95 < 300 мс на 1000 одновременных пользователей
- Безопасность: по shared/security.md; аудит логов ≥ 1 года
- Доступность: 99.5% месяц
- Данные: экспорт/удаление по запросу (если применимо)
```

**MoSCoW** (приоритизация релиза):
- **Must** — без этого релиз бессмысленен;
- **Should** — важно, но есть временный обход;
- **Could** — если будет ресурс;
- **Won't (this release)** — зафиксировано «не в этом релизе» (важно так же, как Must).

**RICE** (когда много Could/Should и ресурс ограничен):
`RICE = (Reach × Impact × Confidence) / Effort` — оценка 1–10, считать просто,
спорить — полезно (выявляет «дорого, но все уверены»).

**INVEST** (проверка user story): Independent, Negotiable, Valuable,
Estimable, Small, Testable. Не-INVEST-история — рефакторить (разбить/объединить/
добавить критерии).

## Правила

1. **Требование = проверяемое утверждение**: «удобный интерфейс» — не
   требование; «новый пользователь завершает onboarding без помощи ≤ 5 мин» — требование.
2. **Won't — в roadmap явно**: «не делаем в этом релизе: X, Y, Z» — защищает от
   scope creep и задаёт границы change control.
3. **NFR — до дизайна**: «безопасно» без чисел — призрачное требование;
   оно должно влиять на архитектурные решения (ADR).
4. **Конфликт требований** фиксируется: два требования не выполняются одновременно →
   решение с приоритетом (в `PROJECT_MEMORY.md`), не «как-нибудь».
5. **Требование изменилось** — новая версия с датой (старая — не удаляется,
   помечается superseded): трассировка не рвётся.

## Интервью (практика)

- Подготовка: цель интервью (какую гипотезу проверяем), 5–7 вопросов,
  30–45 минут.
- Вести: слушать 80% времени; «расскажите подробнее», «дайте пример»,
  «что произошло потом?»; записывать фразы (данные), интерпретации — отдельно.
- Запрещено: предлагать решение в середине, согласовывать («да, точно!»),
  обещать.
- После: конспекты (темы + цитаты) в тот же день → `PROJECT_MEMORY.md`
  (сводка) + решение по гипотезе.

## Питфолы

- **Требование = фича заказчика**: «нужен экспортер в Excel» → спросить задачу
  («для чего экспорт?») → возможно, достаточно отчёта по e-mail.
- **MoSCoW без Won't**: все Must — значит, приоритетов нет.
- **RICE как научная точность**: цифры 7.3 vs 7.1 ничего не значат;
   ценность — в споре и порядке.
- **Интервью как валидация решения**: 10 «отлично, отличная идея» ≠
  валидированное требование (см. discovery: поведение > намерения).
