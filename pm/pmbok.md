# PMBOK — практика для проектов с агентом

**Когда использовать** — структура управления проектом: инициация, планирование,
контроль, закрытие. Полная PMBOK — на 60+ процессов; здесь — то, что реально
используется в проектах с кодинг-агентом.
**Когда НЕ использовать** — тривиальная задача одного дня (overhead > пользы).

## 5 групп процессов

| Группа | Суть | Агентские артефакты |
|---|---|---|
| **Инициация** | Проект существует: цели, стейкхолдеры, полномочия | проект-хартер (1 страница, см. ниже), раздел «Проект» и «Люди» в `PROJECT_MEMORY.md` |
| **Планирование** | Как, когда, сколько, чем рискуем | `roadmap.md` (WBS по фазам), план качества (DoD), реестр рисков |
| **Выполнение** | Делаем работу | код/доставка, коммуникации по чек-листу, работа по roadmap |
| **Мониторинг и контроль** | Отклонения и изменения | статус по каждой итерации, change control, пересмотр рисков на гейтах |
| **Закрытие** | Формальное завершение | проект-закрытие: что сделано, что нет, метрики, уроки (ретро), архив памяти |

## 10 областей знаний — что важно агенту

| Область | Практическое применение |
|---|---|
| Интеграция | Единый план = `roadmap.md`; любое изменение — через change control |
| Охват (scope) | Хартер + scope out; «won't this release» — так же явно, как Must |
| Расписание | Вехи (milestones) в roadmap; буфер, не обещание optimistic-срок (см. [risks.md](risks.md)) |
| Стоимость | Бюджет/лимит (время, деньги, токены); контроль — по вехам |
| Качество | DoD на уровне задачи и фазы; CI зелёный — часть DoD |
| Ресурсы | Кто что делает (RACI); агент — ресурс, у которого нужен контекст (`PROJECT_MEMORY.md`) |
| Коммуникации | Частота/канал отчётов; «тихий» агент = потерянный проект |
| Риски | Реестр (см. [risks.md](risks.md)); пересмотр — каждый гейт |
| Закупки | Внешние сервисы/подрядчики: условия, лимиты, владелец интеграции |
| Стейкхолдеры | Карта стейкхолдеров (властность × заинтересованность), режим общения |

## Проект-хартер (шаблон, 1 страница)

```markdown
# Хартер: <название>
- Проблема: <кто, что болит, почему сейчас>
- Цель (одна): <измеримый результат>
- KPI: <метрика + целевое значение + срок>
- Scope: <входит (Must) / не входит (Won't)>
- Вехи: <M1 — дата, M2 — дата, …>
- Бюджет/лимит: <деньги или «N человеко-дней»>
- Стейкхолдеры: <кто решает, кто участвует, кого уведомляем>
- Top-3 риска: <из реестра>
- Владелец проекта: <имя> / решение по спорным вопросам: <кто>
```

## Change control (правило)

1. Изменение scope/сроков/бюджета **никогда не «тихое»**: предложение → оценка
   последствий (scope, сроки, риски) → решение стейкхолдера.
2. Решение фиксируется **в тот же день**: `roadmap.md` (раздел «Решения» — дата,
   что, кто, почему) + `PROJECT_MEMORY.md` (раздел «Решения»).
3. Отклонённое предложение — тоже решение: записать с причиной (иначе вернётся).

## RACI (маленькая матрица)

| Действие | Р (делает) | А (отвечает) | C (консультируем) | I (уведомляем) |
|---|---|---|---|---|
| Код/фича | агент + dev | tech lead | архитектор | продукт |
| Изменение scope | — | владелец продукта | стейкхолдеры | команда |
| Релиз | dev/release | tech lead | QA | продукт, клиент |

Правило: ровно один А на действие («двое отвечают — никто не отвечает»).

## Питфолы

- **Планирование без инициации**: roadmap без хартера — нет критерия «зачем»,
  scope не ограничен.
- **RACI без А**: у ключевого решения два «ответственных» — решение не принято.
- **Change control «в Telegram»**: решение в чате, а в roadmap старый scope —
  контрольный срез (roadmap) врёт.
- **Закрытие как «перестали работать»**: без ретроспективы и архива памяти
  следующий проект стартует с чистого листа.
