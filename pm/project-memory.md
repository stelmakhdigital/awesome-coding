# Проектная память (`PROJECT_MEMORY.md`) — правила

**Когда использовать** — всегда, когда проект длится дольше одной сессии
агента/разработчика: файл `PROJECT_MEMORY.md` в корне целевого проекта.
**Когда НЕ использовать** — одноразовая задача (контекст не теряется).

## Зачем

Контекст проекта живёт в головах (и историях чатов/сессий), которые
не переживают смену участников и сессию агента. `PROJECT_MEMORY.md` —
единственное место, где новый агент/человек получает: что это за проект,
кто в нём участвует, **что решено и почему**, какие ограничения,
где сейчас проект. Это продолжение практики ADR (см. `shared/documentation.md`),
расширенной на людей, риски и текущее состояние.

## Шаблон

```markdown
# PROJECT_MEMORY: <название>

## 1. Проект (одно предложение)
<что строим, для кого, одна строка>

## 2. Цель и KPI
- Цель: <измеримый результат>
- KPI: <метрика, целевое значение, срок, текущее значение на дату>

## 3. Люди и стейкхолдеры
| Кто | Роль | Решает | Как/сколько часто общаться |
|---|---|---|---|
| <имя> | владелец продукта | scope, приоритеты | e-mail, по решению |
| <имя> | tech lead | архитектура, code review | PR |

## 4. Решения (ADR-lite)
- **2026-09-05 — Платёжка: Stripe.** Почему: международные пользователи
  (опрос 18/40). Альтернативы: Тинькофф (отклонено — нет международных).
  Решение: владелец продукта.
- **2026-09-14 — Без мобильной версии в v1.** Почему: срок; веб покрывает 90%.

## 5. Ограничения и риски (top)
- Бюджет: N человеко-дней (жёстко).
- Top-риск: <из реестра рисков> — митигция: <…>.

## 6. Текущее состояние (свежесть ≤ 1 недели)
- Фаза: 3 Development, итерация 2 (по roadmap.md)
- Следующее: API ядра домена (⬜)
- Обновлено: 2026-09-07

## 7. Глоссарий
- <термин> — <значение в контексте проекта>
```

## Правила

1. **Решение — в день принятия** (дата + кто + почему + отклонённые
   альтернативы). Записывать «вчера» — нормально; «на следующей неделе» — нет.
2. **«Текущее состояние» не старше недели**: устаревший статус хуже его отсутствия
   (читатель доверяет, а он врёт).
3. **Только то, что теряется вне файла**: не дублировать код, схему БД,
   changelog — ссылаться. Записывать: контекст, люди, «почему», ограничения.
4. **Конфликт с фактами — факты выигрывают**: код/метрики отличаются от файла →
   обновить файл (это сигнал, что память устарела), а не «поправить код под память».
5. **Статусы решений**: активное / superseded (заменено датой+ссылкой) / отклонено.
   Отклонённые — не удалять: они объясняют «почему не так, как я бы сделал».
6. **Обновлять на**: конце фазы, после ключевой беседы, при смене человека,
   при принятии решения, раз в неделю (минимум).
7. **Одна запись = одно решение** (не «разное про всё»): трассировка и supersede
   работают только на атомах.
8. **Файл — под версионным контролем** (git): история изменений памяти —
   часть памяти.

## Питфолы

- **Память как дневник**: «сегодня обсудили, завтра решили» — это лог, не память.
  В памяти — решение и контекст, не хроника.
- **Память без людей**: решения без «кто решил» не имеют силы (нельзя
  поспорить с призраком; надо звать человека).
- **Объём**: файл на 2000 строк не читают. Если разросся — архивировать
  superseded/закрытые блоки в `PROJECT_MEMORY-archive.md`, основной — держать
  компактным.
- **Записывать «очевидное»**: «используем PostgreSQL» — в памяти, если это
  осознанное решение с альтернативами; если просто «так в стеке» — не записывать.
